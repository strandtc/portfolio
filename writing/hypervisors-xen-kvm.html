Xen, KVM, and the hardware underneath them

What a hypervisor does to a CPU, why x86 needed hardware help, and how Xen and KVM take different routes to the same place.

Systems8 min read

An operating system is written to believe it owns the machine. It programs page tables, talks to the interrupt controller, pokes devices at fixed physical addresses, and runs privileged instructions assuming nothing else is arbitrating. A hypervisor's entire job is to make that belief survive contact with thirty other operating systems on the same box. Everything above it - the API, the scheduler, the billing - is bookkeeping.

Trap and emulate, and why x86 broke it

The classical technique is trap-and-emulate. Run the guest kernel at lower privilege than it thinks it has. When it executes something privileged, the CPU faults into the hypervisor, which emulates the effect against that guest's virtual machine state and resumes it. Popek and Goldberg formalized the requirement in 1974: an architecture is efficiently virtualizable if every instruction capable of observing or changing privileged state traps when executed outside the privileged mode.

x86 did not meet that bar. It had instructions that touched privileged state and, run at low privilege, simply did something different rather than faulting. No trap, no interception point, and a guest kernel that can quietly discover it isn't really in ring 0. The first generation of x86 virtualization worked around this with binary translation - scanning guest kernel instruction streams at runtime and rewriting the awkward ones. It worked. It was also an enormous amount of machinery to maintain.

Paravirtualization was the other way out

Xen took the opposite approach in 2003. If the hardware won't trap, change the guest. Paravirtualization means modifying the guest kernel so it never issues the problematic instructions at all - instead it makes explicit hypercalls into the hypervisor for page table updates, memory management, and I/O. On 32-bit x86 Xen ran the guest kernel in ring 1, with Xen itself in ring 0 and applications still in ring 3.

The performance was very good, because a paravirtualized guest asks for exactly what it needs instead of tripping a fault and having the hypervisor reverse-engineer intent. The cost was that you needed a ported kernel. That was fine for Linux and impossible for anything you couldn't recompile.

Then the hardware caught up. Intel shipped VT-x in 2005, AMD shipped AMD-V in 2006. Both add a new mode below ring 0: the hypervisor runs in root mode, the guest runs in non-root mode with a full ring 0 through ring 3 of its own, and a control structure defines exactly which events cause a VM exit back to the hypervisor. Suddenly an unmodified guest kernel can run at what it believes is full privilege and still be contained.

Memory was the remaining tax. Early hardware-assisted setups used shadow page tables - the hypervisor maintained its own copy of every guest page table and kept them in sync, which meant a VM exit on every guest page table write. AMD added nested paging with the Barcelona Opterons in 2007; Intel added Extended Page Tables with Nehalem in 2008. Two-level translation in hardware. Guest virtual to guest physical to host physical, walked by the MMU, no hypervisor involvement. That single change did more for virtualization density than anything else in the decade.

Xen's dom0 versus KVM as a kernel module

Xen boots first. It is a small hypervisor that takes the hardware, then starts a privileged guest called dom0 - normally Linux - which owns the physical device drivers and runs the toolstack. Unprivileged guests are domUs, and their I/O goes through split drivers: a frontend in the guest, a backend in dom0, connected over shared memory rings and event channels. Xen itself stays small and stays out of the data path for storage and network.

KVM inverted that. Avi Kivity's insight at Qumranet was that Linux already is a hypervisor in every respect except the CPU mode switch - it has a scheduler, a memory manager, and every device driver anyone has ever written. So KVM is a kernel module that exposes VT-x and AMD-V through a device node. It merged into Linux 2.6.20 in February 2007. A virtual machine is a process. Its vCPUs are threads. The Linux scheduler schedules them. top shows them. cgroups constrain them. The userspace half - device models, machine construction, migration - lives in QEMU or something smaller.

Both models work. The practical differences show up in operations, not benchmarks:

Running both in production is instructive. Xen's separation is real and it buys you something - the hypervisor is a smaller, slower-moving thing than a general purpose kernel. KVM's integration is also real, and it buys you the fact that every tool your systems people already know keeps working. Storm on Demand, the IaaS platform I helped build at Liquid Web, ran on both before mainstream cloud existed, and the operational cost of KVM was lower simply because there was less that was special about it.

The I/O problem, and virtio

Emulating a real network card - an e1000, say - means the guest driver writes to a register, that write causes a VM exit, userspace decodes it, and eventually a packet moves. It is correct, it works with any guest, and it is slow, because you are paying an exit per register access on a device designed for a machine where register access was free.

virtio, which Rusty Russell wrote up in 2008 and OASIS later standardized, replaces emulation with an honest shared-memory queue. A descriptor ring the guest fills, an available ring it publishes, a used ring the host returns. One notification amortized over many buffers instead of an exit per access. It is paravirtualization applied to devices only, and it is the reason a hardware-assisted guest with virtio drivers outperforms a fully paravirtualized guest with emulated ones.

Below virtio there is passthrough. Give the guest a real PCI device, and use the IOMMU (VT-d, AMD-Vi) to constrain the DMA that device can issue so a guest cannot program it to write over the host's memory. SR-IOV makes that economical: a PCI-SIG extension where one physical function advertises many lightweight virtual functions, each with its own requester ID and BARs, each assignable to a different guest. The NIC does the switching in silicon.

The catch is that once a guest owns real hardware, you can no longer live-migrate it. There is no way to serialize the state sitting inside that VF. That single constraint tends to decide the architecture: if your product promise is "we can move your instance off a failing host without you noticing," you use virtio and you accept the CPU cost.

Memory overcommit, and where it bites

You can oversubscribe CPU comfortably because most workloads are idle most of the time and the scheduler sorts it out. Memory is different. A guest touches a page and it needs to exist.

Three mechanisms make overcommit survivable. Ballooning puts a driver in the guest that allocates pages on request and tells the hypervisor those pages are free to reclaim - the guest's own allocator does the choosing, which is far better than the host guessing. Kernel samepage merging scans anonymous pages and collapses identical ones to a single copy-on-write page, which pays off spectacularly on a host running forty copies of the same distribution and not at all on a host running forty different databases. And underneath both, the host can just swap guest memory, which is the option you never want taken.

The failure mode is not gradual. A host that is 10% overcommitted performs fine until several guests grow at once, and then it swaps, and swapping under a guest is worse than swapping under a process because the guest has already made its own paging decisions on the assumption its memory is real. Ballooning too aggressively produces the same thing from the other direction: the guest OOM-kills something because you took its page cache away.

What containers changed

Containers did not replace the hypervisor; they replaced the reason most people were using one. Namespaces and cgroups give you separate views of the process table, network stack, and filesystem, plus enforced resource limits, with one shared kernel and no emulation of anything. If what you wanted was to run ten services on one machine without them stepping on each other, that is the cheaper answer and it always was.

What you give up is the boundary. A container escape is a kernel bug. A VM escape has to get through the CPU's own isolation mode first. That distinction is why the industry swung part of the way back: Firecracker, which AWS open-sourced in 2018 to run Lambda, is a minimal VMM on KVM with the device models stripped down to almost nothing - AWS quotes boot times around 125 ms and under 5 MiB of memory overhead per microVM. Hardware isolation at close to container startup cost.

The rule of thumb hasn't moved much: use containers between things you trust, use a hypervisor between things you don't. If the tenants on either side of the boundary are different customers, the boundary needs to be enforced by the CPU.
