Building your own kernel, and the bill that comes with it

What a custom Linux kernel actually buys you, how to manage the config, and the ongoing maintenance you are agreeing to.

Systems8 min read

Building a kernel is easy. make defconfig, make -j, done. Running your own kernel across a fleet for five years is not easy, and the gap between those two facts is where most of the trouble lives. So the question is never "can I build a kernel." It's "what do I get, and what am I signing up to do every month for the life of these machines."

What you actually gain

Be honest about the list, because it's shorter than people expect.

A feature or driver your distribution doesn't ship. This is the legitimate reason and it accounts for most real cases. New hardware whose driver landed after your distribution's kernel forked. A filesystem or a networking feature that isn't backported. Something like PREEMPT_RT for latency-sensitive work, before it merged upstream.

A patch you need and can't wait for. A fix in mainline that hasn't reached your vendor's tree yet, or a change nobody upstream is going to accept because it only makes sense for your workload.

Attack surface reduction. Compiling out subsystems you don't use is real hardening, and it's the kind an auditor can see. It's also worth less than turning off the modules you don't load, which costs nothing.

Tuning that has to be compile-time. Timer frequency, preemption model, page size on some architectures, debug and instrumentation options. Most of what people want to tune is a sysctl or a boot parameter, so check that first - the number of "custom kernels" that exist to change something you could have set in /etc/sysctl.d is not small.

What you almost never get is meaningful throughput. Compiling out unused drivers doesn't speed anything up; unloaded code doesn't execute. If someone is proposing a kernel build for performance, ask what they expect to measure and how.

Config management, which is the actual work

The kernel has tens of thousands of config symbols and they are the deliverable. The build is reproducible; the config is the thing you maintain.

Start from a defconfig, never from make menuconfig on a blank slate. arch/x86/configs/x86_64_defconfig is a sane, tested baseline. Then express your changes as fragments - small files containing only the symbols you're overriding - and merge them:

make x86_64_defconfig
scripts/kconfig/merge_config.sh -m .config \
    fragments/hardening.config \
    fragments/storage.config \
    fragments/site-local.config
make olddefconfig

olddefconfig accepts the default for anything new rather than prompting, which is what you need in CI. savedefconfig writes back the minimal set of non-default symbols, which is what you want to commit; a full .config is fifteen thousand lines of noise and produces unreviewable diffs.

make localmodconfig deserves a mention and a warning. It reads lsmod and disables everything not currently loaded. On a running machine it produces a small, fast-building kernel. On a fleet it produces a kernel that fails to boot on the next hardware revision, because the driver for the new NIC wasn't loaded on the box you generated it from. Use it to explore, not to ship.

The rule that saves you: every kernel upgrade means re-running olddefconfig against your fragments and reading what changed. New symbols appear every release and their defaults are not always what you want. If nobody reads that diff, you don't have a config, you have a sediment.

Module or built-in

=y compiles into the image, =m builds a loadable module, =n leaves it out.

Built-in is right for anything needed to reach the root filesystem, if you'd rather not maintain an initramfs, and for things you want present unconditionally. Modules are right for everything else, because they keep the image small, let you ship drivers separately, and let you blacklist something at boot without a rebuild.

The security argument is where people talk past each other. A monolithic kernel with CONFIG_MODULES=n cannot have a malicious module loaded into it, which is genuinely stronger. But then adding a driver means a reboot, and you've lost the ability to fix a hardware problem at 3am without a maintenance window. Most fleets are better served by keeping modules and enforcing signatures - CONFIG_MODULE_SIG_FORCE with your own key - which gets most of the benefit and none of the rigidity.

Mainline, longterm, or the distribution kernel

Three sources, three different deals:

Mainline / stableLongterm (LTS)Distribution kernel
Release cadence~9-10 weeksYearly designationPer major release
Fixes you getEverything, fastBackported stable fixesVendor-selected backports
Version number tells youReal upstream versionReal upstream versionAlmost nothing
ABI stabilityNoneNone across minor bumpsDeliberately maintained
Who owns a regressionYouYouYour vendor

The distribution kernel is the option people underrate because the version number looks ancient. RHEL 7 shipped 3.10, RHEL 8 shipped 4.18, RHEL 9 shipped 5.14 - and none of those numbers describe the code. Red Hat backports fixes and features into that base for the life of the release, and maintains a stable kernel ABI within a minor release so third-party modules keep loading, with the stated exception that they will break it if a serious security issue can't be fixed otherwise. When Liquid Web ran thousands of servers, most of them CentOS, that ABI promise was worth more than any feature in a newer tree, because it meant storage and monitoring modules kept working across updates.

Longterm kernels are the middle path. Worth knowing: the stable maintainers reduced the default support window for new LTS kernels from six years to two in 2023, on the reasoning that almost nobody was actually running the old branches. Two years is a default rather than a hard limit and branches do get extended, but if you're planning a product lifecycle around a longterm kernel, check the current end-of-life date rather than assuming the old six-year figure.

Patching, and what it costs

If you carry patches, carry them as a series, not as a modified tree. git format-patch output, or quilt, applied in order onto a tagged upstream release. The moment someone commits directly to a fork, you've lost the ability to tell your changes from upstream's, and the next rebase becomes an archaeology project.

Budget for the rebase, because it recurs. Every upstream release can move the code your patch touches. A small, well-isolated patch against a stable interface might survive years untouched. A patch in the scheduler or the memory management code will need attention every cycle. The strongest argument for getting a change upstream isn't ideology, it's that upstream then maintains it for you.

The other cost is the one that shows up when you need help. Running an unpatched vendor kernel means a support case. Running your own means you own the bisect. That's fine if you have people who can bisect a kernel, and expensive if you don't.

Packaging so a fleet can actually consume it

A kernel you install with make modules_install install is a science project. A kernel your fleet can consume is a package in a repository with a version, a changelog, and a rollback.

The kernel tree will do most of this for you:

make -j"$(nproc)" binrpm-pkg     # binary RPM only
make -j"$(nproc)" bindeb-pkg     # binary deb only
make -j"$(nproc)" rpm-pkg        # source and binary RPMs

That gets you a package. Turning it into something operable takes a few more decisions.

Version it so that ordinary package tooling upgrades cleanly and downgrades on demand - the release field is where your build number goes, and it must monotonically increase. Ship the matching kernel-devel or linux-headers package or every DKMS module on the fleet breaks. Keep at least the previous kernel installed and present in the boot menu; the correct response to a kernel that doesn't come back up is a reboot to the old one, and that only works if you left it there. Sign the package, and if the fleet runs secure boot, sign the kernel image and the modules too.

Then stage it. Build, install on a canary rack, leave it under real load for longer than feels necessary, then roll by failure domain. Kernel bugs are rarely instant. Memory leaks, lock contention under load, a driver that misbehaves only after a link flap - these show up on day four, not minute four.

Before you start any of this, one test: write down what the custom kernel does that the vendor kernel doesn't, in one sentence, in terms of a workload. If you can't, you've found a hobby, not a requirement. If you can, put a review date on it - every year, check whether that reason still holds, because the usual ending for a custom kernel program is that the feature landed upstream three releases ago and nobody noticed.
