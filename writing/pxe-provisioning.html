Network booting a fleet without touching it

How PXE, iPXE, UEFI and out-of-band control fit together, and what it takes to make an install repeatable across thousands of machines.

Systems8 min read

A rack of new servers arrives. Nobody should ever plug a keyboard into one. From the moment they're cabled and powered, everything - firmware settings, disk layout, OS, kernel, packages, config management enrollment - should happen over the wire, the same way, every time. That is the whole objective. The mechanisms below are just the ways it goes wrong.

What actually happens when a machine PXE boots

The NIC's option ROM broadcasts a DHCP DISCOVER like any other client, but with extra baggage. It sets option 60 (vendor class identifier) to a string starting PXEClient, and option 93 (client system architecture) to a number telling you what kind of firmware is asking. That number matters more than anything else in the transaction, because it determines which boot file you must hand back.

The DHCP server replies with an address plus option 66 (TFTP server name) and option 67 (boot file name), or the equivalent BOOTP next-server and filename header fields - set both, because plenty of clients only read one. The firmware then fetches the named file over TFTP and executes it.

That's it. DHCP tells you where to go and what to get; TFTP gets it. Everything modern is a workaround for one of those two protocols.

Option 93 is where the mismatches live

The architecture types are an IANA registry, originally from RFC 4578 and extended for UEFI HTTP boot:

There is one long-standing trap here. RFC 4578 labeled type 7 as "EFI BC" and type 9 as "EFI x86-64", while the UEFI specification and effectively every shipping implementation use 7 for x64 UEFI. Follow the hardware, not the RFC text: 7 is what a normal 64-bit UEFI server sends. If you inherited a DHCP config written by someone who read the RFC literally, that is the bug.

In ISC dhcpd this is a class match on the option; in dnsmasq it's dhcp-match. Either way, the shape is the same - branch on option 93, hand back a different file. Get it wrong and the symptom is unhelpful: the firmware fetches a file, fails to execute it, and either loops or falls through to the next boot device with no message you'll ever see.

TFTP is the bottleneck, and iPXE is the fix

TFTP as specified in RFC 1350 is lockstep with 512-byte blocks. Send a block, wait for the ack, send the next. Over UDP, on a network with any latency at all, that is dismal. RFC 2348 added a negotiable block size - practically capped around 1468 bytes so you don't fragment a standard Ethernet frame - and RFC 7440 added a window size so multiple blocks can be in flight. Turn both on. It is the single cheapest improvement to a slow PXE environment.

The better answer is to stop using TFTP for anything large. iPXE is open source boot firmware that speaks HTTP, HTTPS, iSCSI, and more, and it can be chainloaded: TFTP delivers one small iPXE binary - undionly.kpxe for BIOS clients, ipxe.efi for UEFI - and everything after that is HTTP. Kernel, initrd, and squashfs over HTTP from a normal web server you already know how to scale, cache, and monitor.

Chainloading has an obvious hazard. iPXE issues its own DHCP request, gets told to load iPXE, and loops. The standard escapes are to test for iPXE in the DHCP request (iPXE identifies itself and sets a user class) and serve it a script instead of a binary, or to build iPXE with the script embedded so it ignores DHCP's opinion entirely. The embedded-script build is more work up front and much harder to break later, which is the trade you usually want at fleet scale.

Newer UEFI firmware can do HTTP boot natively - architecture types 15 and 16, with option 60 set to HTTPClient and option 67 containing a URL. It removes the TFTP step entirely. It is also the part of any given firmware that has been tested least, so verify it per platform before you build a workflow on it.

Secure boot complicates all of this

With secure boot enabled, the firmware only executes binaries signed by a key in its db. In practice that means Microsoft's third-party UEFI CA, because that's the key that ships in the db of essentially every x86 server. The distributions solve it with shim: a small Microsoft-signed loader that then verifies the next stage - GRUB, and then the kernel - against the distribution's own embedded certificate, plus a Machine Owner Key list you can add to.

So the chain is firmware to shimx64.efi to grubx64.efi to vmlinuz, and every link is signature-checked. Two consequences for provisioning:

Unsigned iPXE won't run. If you want both secure boot and iPXE, you sign your own iPXE build and enroll your key, which means owning a signing key and the process around it.

Your custom kernel won't boot either, and neither will your out-of-tree modules. You generate a MOK key pair, enroll the public certificate with mokutil, and sign the kernel and modules. MOK enrollment is interactive at the console by design - that is the point of it - so at fleet scale you're either scripting key enrollment through the vendor's firmware API or deciding that the machines running your custom kernel don't run secure boot. Decide that deliberately, once, and write it down.

Out-of-band: IPMI and Redfish

None of the above helps if you can't force a machine to net-boot or read why it didn't.

IPMI is the old answer - a command model over UDP, usually port 623, spoken to the BMC with ipmitool. It does what you need: power on, power cycle, set the next boot device to PXE, open a serial-over-LAN console, read sensors. It also has a security history nobody defends, and Intel has stated that no further updates to the specification are planned and points users toward more modern interfaces.

Redfish is that interface: a DMTF standard, a JSON schema-based REST API over HTTPS. Same operations, but discoverable and scriptable without a special client.

# force the next boot to PXE, then power on
curl -sk -u admin:$PW -X PATCH \
  -H 'Content-Type: application/json' \
  -d '{"Boot":{"BootSourceOverrideTarget":"Pxe",
               "BootSourceOverrideEnabled":"Once"}}' \
  https://$BMC/redfish/v1/Systems/1

curl -sk -u admin:$PW -X POST \
  -d '{"ResetType":"On"}' \
  https://$BMC/redfish/v1/Systems/1/Actions/ComputerSystem.Reset

Redfish also covers the thing IPMI never did well: firmware and BIOS settings as data. Being able to GET a BIOS attribute set from one machine and PATCH it onto four hundred others is the difference between a fleet and a collection. Vendor coverage varies - check what your platform actually implements before you assume a schema exists.

The unattended install

Kickstart on the Red Hat side, preseed on Debian, autoinstall on modern Ubuntu. All three do the same job: answer every installer question in advance, from a file the installer fetches over the network.

The discipline that matters isn't the syntax, it's restraint. A kickstart with four hundred lines of %post shell is a configuration management system with no state, no idempotence, and no way to test a change other than reinstalling a server. Keep the install to the things that genuinely can only happen at install time - partitioning, bootloader, base package set, network - and hand off to your config management tool at first boot. The install should be boring and identical; the divergence belongs somewhere it can be converged.

Serve the config file over HTTP from something that knows the machine, keyed on MAC address or serial. That way "what will this host install as" is a question you can answer with curl before you power it on.

Making it actually repeatable

Every failure I've seen at scale traces back to a machine that was not identical to its neighbors in a way nobody had recorded. So:

Version the firmware and the BIOS settings, and check them as part of provisioning rather than trusting what shipped. Two servers from the same PO can have different microcode and different boot orders.

Make the boot menu deterministic and time out to nothing. A netboot default that installs is a loaded gun; anything that reboots unexpectedly will find it.

Log both sides. The DHCP transaction and the HTTP fetches, together, tell you exactly where a machine stopped. Without them you're guessing at a black screen.

And treat "install completed" as untrusted. Have the machine report in and prove itself: right kernel, right disks, right link speeds, right BMC credentials. A build that silently succeeded wrong is more expensive than one that failed loudly.
